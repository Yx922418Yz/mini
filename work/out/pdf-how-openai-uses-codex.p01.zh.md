# OpenAI 如何使用 Codex

（原文页码：3）

## 引言

Codex 每天被 OpenAI 的众多技术团队使用，包括安全、产品工程、前端、API、基础设施和性能工程等团队。团队用它来加速各类工程任务，从理解复杂系统、重构大型代码库，到交付新特性、在紧迫时限内解决线上事故。

基于对 OpenAI 工程师的访谈以及内部使用数据，我们汇总了一批用例与最佳实践，用以说明 Codex 如何帮助我们的团队更快推进、提升工作质量，并在规模化场景下管理复杂性。

---

## 用例 1：代码理解

（原文页码：4）

在入职、调试或排查事故时，Codex 帮助我们的团队快速熟悉代码库中陌生的部分。

团队常用 Codex 来定位某个功能的核心逻辑、梳理服务或模块之间的关系，以及追踪数据在系统中的流转。它还能帮助浮现架构模式，或补上那些原本需要大量人工才能生成的缺失文档。

在事故响应期间，Codex 通过呈现组件之间的交互、追踪故障状态如何在各系统间传播，帮助工程师迅速进入陌生领域。

**来自我们团队的轶事**

- “修 bug 时，我用 Ask 模式看看代码库里还有哪些地方可能出现同样的问题。”——性能工程师，检索系统
- “值班时，我把堆栈跟踪粘进去，问 Codex 认证流程在哪里。它直接跳到正确的文件，让我能快速分诊。”——站点可靠性工程师，API 平台
- “对于横跨 Terraform 和 Python 的‘我该在哪里做这件事？’这类仓库问题，Codex 回答得比 grep 快得多。”——DevOps 工程师，基础设施服务

**试试用这些示例提示让 Codex 做代码理解：**

- 这个仓库里认证逻辑实现在哪里？
- 总结请求从入口到响应是如何流经这个服务的。
- 哪些模块与 [填入模块名] 交互，失败又是如何处理的？

## 用例 2：重构与迁移

（原文页码：5）

Codex 常用于进行跨多个文件或包的改动。例如，当工程师更新 API、改变某个模式的实现方式，或迁移到新依赖时，Codex 能让改动被一致地应用。

当同一个更新需要在数十个文件中完成，或该更新要求理解用正则、查找替换难以捕捉的结构与依赖关系时，它尤其有用。

团队也用它做代码清理：拆分过大的模块、用现代模式替换旧模式，或为更好的可测试性做代码准备。

**来自我们团队的轶事**

- “Codex 把每一个旧的 `getUserById( )` 都换成了我们的新服务模式，并开了 PR。几分钟就干完了本该花几小时的事。”——后端工程师，ChatGPT Web
- “为了清除上线阻塞项，我让 Codex 扫描旧模式的每一处实例，用 Markdown 总结影响，然后带着修复开 PR。”——产品工程师，ChatGPT Enterprise

**试试用这些示例提示让 Codex 做重构与迁移：**

- 按关注点把这个文件拆成独立模块，并为每个模块生成测试。
- 把所有基于回调的数据库访问改成 async/await。

## 用例 3：性能优化

（原文页码：6）

Codex 被用来定位并处理性能瓶颈。

在调优或可靠性工作中，工程师会让 Codex 分析缓慢或内存密集的代码路径，比如低效循环、重复操作或昂贵的查询，并给出优化建议，往往带来效率与可靠性上的显著提升。

Codex 也用于维护代码健康：识别仍在使用中的高风险或已废弃模式。我们的团队依靠它来减少长期技术债、主动预防回归。

**来自我们团队的轶事**

- “我用 Codex 扫描重复的昂贵数据库调用。它很擅长标出热点路径，并起草稍后可以再调优的批量查询。”——基础设施工程师，API 可靠性
- “Codex 很擅长快速发现性能问题——花 5 分钟写提示，省下 30 分钟的工作。”——平台工程师，模型服务

**试试用这些示例提示让 Codex 做性能优化：**

- 为内存效率优化这个循环，并解释你的版本为什么更快。
- 找出这个请求处理函数中重复的昂贵操作，并给出缓存机会建议。
- 为这个函数提出一种更快的批量数据库查询方式。

## 用例 4：提升测试覆盖率

（原文页码：7）

Codex 帮助工程师更快地写测试——尤其是在覆盖率薄弱或完全缺失的地方。

在处理 bug 修复或重构时，工程师常让 Codex 建议覆盖边界情况或可能失败路径的测试。对于新代码，它可以根据函数签名和周边逻辑生成单元测试或集成测试。

在识别边界条件方面，Codex 尤其有用，比如空输入、最大长度，或那些常被初始测试遗漏、罕见但合法的状态。

**来自我们团队的轶事**

- “我让 Codex 通宵处理低覆盖率模块，早上醒来就收到可运行的单元测试 PR。”——前端工程师，ChatGPT Desktop
- “当切换单体仓库分支很痛苦时，我让 Codex 写测试并启动 CI，同时我继续在自己的分支上干活。”——后端工程师，支付与计费

**试试用这些示例提示让 Codex 提升测试覆盖率：**

- 为这个函数编写单元测试，包括边界情况和失败路径。
- 为这个排序工具生成一个基于属性的测试。
- 扩展这个测试文件，覆盖围绕空输入和非法状态缺失的场景。

## 用例 5：提升开发速度

（原文页码：8）

Codex 通过加速开发周期的开头与结尾，帮助团队更快推进。

在启动新特性时，工程师用它来搭建样板代码——生成文件夹、模块和 API 桩，快速让代码跑起来，而不必手工接线每一处。

当项目接近发布时，Codex 通过处理更小但关键的任务帮助赶上紧迫期限，比如分诊 bug、补上最后一公里的实现缺口，以及生成发布脚本、遥测钩子或配置文件。

它也被用来把产品反馈变成起步代码。工程师常把用户需求或规格粘贴进去，让 Codex 生成一份粗略草稿，之后再回头打磨。

**来自我们团队的轶事**

- “我整天都在开会，却仍然合并了 4 个 PR，因为 Codex 在后台替我干活。”——产品工程师，ChatGPT Enterprise
- “Codex 帮我完美交付了 3–4 个低优先级修复，否则它们会一直烂在 backlog 里，这让人特别有掌控感。”——全栈工程师，内部工具

**试试用这些示例提示让 Codex 提升开发速度：**

- 为 `POST /events` 搭建一条新的 API 路由，带基础校验和日志。
- 用这个模板 [插入你的遥测代码示例] 生成一个遥测钩子，用于追踪新引导流程的成功/失败。
- 基于这份规格创建一个桩实现：[插入规格或产品反馈]。

## 用例 6：保持心流

（原文页码：9）

当工程师的日程被碎片化、充斥着打断时，Codex 帮助他们保持高效。

它被用来接住未完成的工作、把笔记变成可运行的原型，或分流出可以稍后再回看的探索性任务。这让暂停与恢复工作变得更容易，而不至于丢失上下文，尤其是在他们值班或会议繁多的时候。

**来自我们团队的轶事**

- “如果我顺手发现一个能立刻改掉的问题，我就发一个 Codex 任务，而不是切分支，等有空时再审查它的 PR。”——后端工程师，ChatGPT API
- “我习惯把 Slack 讨论串、Datadog 链路、issue 等直接转发给 Codex，这样我就能专注在高优先级工作上。”——API 工程师，基础设施可观测性

**试试用这些示例提示让 Codex 帮你保持心流：**

- 生成一份把这个服务重构成更小模块的计划。
- 把重试逻辑搭出桩来并加一个 TODO——退避逻辑我稍后再补。
- 总结这个文件，好让我明天能接着上次的地方继续。
