## 用例 7：探索与构思

Codex 对开放式工作同样有用，比如寻找替代方案或验证设计决策。你可以让它给出解决问题的不同方式、探索不熟悉的模式，或对假设进行压力测试。这有助于呈现取舍、扩展设计选项、打磨实现选择。

它也被用来识别相关的 bug。给定一个已知问题或已废弃的方法，Codex 能找出代码中别处的相似模式，让捕捉回归或完成清理工作变得更容易。

**来自我们团队的轶事**

- “Codex 帮我解决冷启动问题——我粘进规格和文档，它就搭出代码，或指出我漏掉了什么。”——产品工程师，ChatGPT Desktop
- “修完一个 bug 后，我会问 Codex 类似的 bug 还可能藏在哪，然后分流出后续任务。”——性能工程师，检索系统

**试试用这些示例提示让 Codex 做探索与构思：**

- 如果这个系统是事件驱动而非请求/响应式的，会怎么运作？
- 找出所有手动拼接 SQL 字符串、而没使用我们查询构建器的模块。
- 用更函数式的风格重写这段代码，避免可变状态和副作用。

## 最佳实践

（原文页码：11）

当 Codex 获得结构、上下文和迭代空间时，它表现最好。以下是 OpenAI 各团队正在养成的一些习惯，用以在日常工作中稳定地从中获益。

**从 Ask 模式开始**

对于较大的改动，先用 Ask 模式让 Codex 给出一个实现计划，再把这份计划作为你切到 Code 模式后后续提示的输入。这种两步流程能让 Codex 有据可依，并帮助避免输出中的错误。Codex 在边界清晰的任务上表现最佳——这类任务大约需要你或一位同事花一小时完成，或实现几百行代码。随着模型进步，可以预期它能承担的任务规模会变大。

**迭代式地改进 Codex 的开发环境**

设置启动脚本、环境变量和互联网访问，能显著降低 Codex 的错误率。在运行任务时，留意那些可以在 Codex 环境配置中修正的构建错误。这可能需要几轮迭代，但长期看会带来显著的效率提升。

**像写 GitHub Issue 那样组织你的提示**

当提示的写法与你描述一次 PR 或 issue 中改动的方式一致时，Codex 的响应更好。这意味着要在相关时包含文件路径、组件名、diff 和文档片段。使用诸如“按照 [模块 X] 里的做法来实现这个”这类模式写提示，能改善结果。

**把 Codex 任务队列当作轻量 backlog**

把那些旁支想法、半成品工作或顺手的小修复都发成任务。不必强求一次就生成完整的 PR。Codex 很适合当作一个暂存区，等你重新进入专注状态时再回头处理。

**用 AGENTS.md 提供持久上下文**

维护一个 AGENTS.md 文件，帮助 Codex 在你的仓库中跨多次提示更有效地工作。这类文件通常包含命名约定、业务逻辑、已知的坑，或 Codex 无法仅从代码推断出的依赖关系。关于如何组织 AGENTS.md 文件，可在文档中了解更多。

**善用“Best of N”改善输出**

Best-of-N 功能让你可以同时为一个任务生成多个回复，快速探索多种方案并挑出最好的。对于更复杂的任务，你可以审查多个迭代版本，并把不同回复的片段组合起来，得到更强的结果。

## 展望未来

Codex 仍处于研究预览阶段，但它已经在我们构建软件的方式上产生了真实影响，帮助我们更快推进、写出更好的代码，并承接那些原本永远不会被排上优先级的工作。我们对前方的潜力感到兴奋——随着模型变强、Codex 更深度地融入我们的工作流，我们期待解锁用它开发软件的更多强大方式。我们会继续分享一路上学到的东西。
