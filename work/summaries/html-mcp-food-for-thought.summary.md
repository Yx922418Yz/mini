# MCP: Food for Thought（导读）

> 来源：MCP 相关评论文（Simon Willison 风格）· 文章 id：`html-mcp-food-for-thought` · 原文约 4.3K 字符

## 核心主张
Model Context Protocol（MCP）已成为让 LLM 调用现成工具的**事实标准**，从而把模型变成 Agent。但"把已有 Web API 用 OpenAPI 元数据自动转成 MCP 工具"的常见做法**能跑，但效果并不好**。作者给出四点原因。

## 四点原因（原文要点）
1. **Agent 应付不了大量工具**：VS Code 硬上限 128 个工具，而很多模型远在此前就难以准确调用；每个工具及其描述都占用宝贵的上下文窗口。多数 Web API 并非为此设计，逐 API 映射会导致工具爆炸。而从零设计的 MCP 工具通常更灵活，一个工具可抵多个 API。
2. **API 会迅速吃光上下文窗口**：设想一次返回 100 条、每条 50 字段的记录；即便只需几个字段，所有字段也会进入上下文。分页按"记录数"而非"大小"，单条记录可能占 10 万 token，也可能只占 10 个。JSON 又是 token 效率很低的格式——同样的数据用 **CSV/TSV/YAML** 表示只需约一半 token。
3. **API 没能发挥 Agent 的独特能力**：API 返回给程序消费的结构化数据，而 Agent 还能处理更自由形式的指令，例如 `ask_question` 工具对文档做 RAG 后返回纯文本以指导下一次调用，或 `search_cities` 返回结构化列表**并附带"下一步该调用 get_city_details"的建议**——这种分层与工具链式调用在自动转换时会被完全错过。
4. **若 Agent 需要调 API，它可以自己调**：Claude Code 这类 Agent 已能编写并执行调用 Web API 的脚本；随着沙箱快速成熟，"直接调用、去掉中间层"也许更划算。作者不同意"MCP 根本不需要"的极端结论，但主张顺势而为。

## 结论
Agent 与 API 的典型消费者**本质不同**。自动从现有 API 生成 MCP 工具虽可行，但作者见过的多数服务器都没做字段投影、结果截断/摘要、JSON→CSV/YAML 转换等必要的适配。
